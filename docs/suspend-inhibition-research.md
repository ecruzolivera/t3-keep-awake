# Suspend inhibition for local T3 Code work

Research date: 2026-11-06. Recommendation: keep the existing single user-service supervisor and supervised `systemd-inhibit --no-ask-password --what=sleep --mode=block` backend. Obtain activity through T3's authenticated V2 shell subscription with a narrowly paired `orchestration:read` session. This is the simplest supported integration available in the inspected source. **It is reliable for reported activity, but the shell contract cannot perfectly implement “all local finite work, never devservers.”** Do not claim that stronger guarantee without upstream activity/locality metadata. Evidence and policy implications follow.

## Inhibition backend

`org.freedesktop.login1.Manager.Inhibit("sleep", who, why, "block")` on the system bus returns a Unix FD; closing every duplicate releases the lock. Direct D-Bus is the smallest lifetime model **if** the runtime already supports Unix FD receipt and ownership. Returning a printed FD number from a short-lived bus utility cannot transfer ownership to Node. [login1 API, v257 lines 682–696](https://github.com/systemd/systemd/blob/v257/man/org.freedesktop.login1.xml#L682-L696).

For this dependency-free Node companion, retain the official CLI wrapper rather than adding a D-Bus binding solely for FD passing. It calls precisely that API, acquires the inhibitor before starting its command, then waits for the command. Its parent owns the inhibitor FD; the exec'd helper does **not** inherit that FD: the source duplicates it with close-on-exec and forks with `FORK_CLOSE_ALL_FDS`. The helper's stdin lease still works: supervisor death closes the pipe, helper exits, wrapper finishes, wrapper closes its FD. Correct the existing “inherited inhibitor fd” explanation when implementation documentation is next updated. [systemd-inhibit source, v257 lines 37–52 and 266–325](https://github.com/systemd/systemd/blob/v257/src/login/inhibit.c#L266-L325).

Keep one inhibitor for the aggregate predicate “any qualifying local work”; release when false. Require helper readiness and handle acquisition denial/early exit as a visible failure. `KillMode=control-group` supplies service-level cleanup for wrapper and helper on stop/failure; normal FD closure supplies lock cleanup after process death. Restart may leave a brief unprotected interval, and neither a frozen supervisor nor a permanently stuck helper is solved by FD lifetime alone. Do not hold a wrapper around the entire always-running monitoring service. [systemd kill semantics, v257 lines 56–90](https://github.com/systemd/systemd/blob/v257/man/systemd.kill.xml#L56-L90); existing [inhibitor implementation](../lib/inhibitor.mjs).

### What each lock means on this desktop

- `sleep:block` addresses suspend/hibernate; `delay` is a bounded preparation window, not a work-duration lock. `block-weak` may be ignored by the same user and is unsuitable for preventing that user's DMS suspend. A sleep blocker can fail an ordinary manual suspend too; there is no automatic-vs-manual distinction in this lock. Privileged/explicit override paths remain possible. [Official inhibitor specification](https://systemd.io/INHIBITOR_LOCKS/).
- `idle:block` gates logind's own idle action. DMS has its own idle timer and issues explicit suspend, so that lock alone does not cover its suspend path. logind requires idle sessions and no idle inhibitor for `IdleAction`. [logind configuration](https://www.freedesktop.org/software/systemd/man/latest/logind.conf.html#IdleAction=); DMS sources below.
- Screen/Wayland idle inhibition changes desktop idleness and can suppress display-off and locking as well as suspend. Avoid DMS “keep awake” and screensaver inhibition for this task: DMS gates its display, lock, and suspend timers on its own inhibitor state and `screensaverInhibited`; post-lock display-off has a separate gate. A login1 sleep lock does not set these QML flags. [DMS IdleService v1.6.3 lines 16–49](https://github.com/AvengeMedia/DankMaterialShell/blob/v1.6.3/quickshell/Services/IdleService.qml#L16-L49).

Installed `IdleService.qml` lines 139–149 raises `requestSuspend`; lines 186–187 call `SessionService.suspendWithBehavior`. Installed `SessionService.qml` lines 449–498 selects `systemctl` on systemd Linux, with a loginctl fallback, then suspend or suspend-then-hibernate. Custom suspend commands can replace the normal path. Upstream has the same power-command functions at those line numbers; upstream IdleService is offset. Thus inference: sleep inhibition should block ordinary DMS auto-suspend while leaving its separate lock/display timers enabled, subject to actual commands and authorization. This was source-verified, not experimentally exercised. [Upstream IdleService suspend path](https://github.com/AvengeMedia/DankMaterialShell/blob/v1.6.3/quickshell/Services/IdleService.qml#L130-L182), [SessionService](https://github.com/AvengeMedia/DankMaterialShell/blob/v1.6.3/quickshell/Services/SessionService.qml#L449-L498).

Lid behavior needs precision: logind defaults `LidSwitchIgnoreInhibited=yes`, so logind-handled lid-close normally ignores high-level sleep blockers. Desktop-owned lid handling can differ. Sleep/power keys normally respect high-level inhibitors. Do not promise either “lid always works” or “lid always blocked.” No low-level handle-key/lid inhibitor is needed. [logind key/lid configuration](https://www.freedesktop.org/software/systemd/man/latest/logind.conf.html#LidSwitchIgnoreInhibited=).

Critical battery is not guaranteed exempt by a `sleep:block` lock. If a power manager requests ordinary suspend/hibernate and honors locks, the blocker can interfere; privileged override, shutdown, and eventual hardware power loss are separate paths. Installed DMS `BatteryService.qml` critical handling around lines 220–260 sends alerts; the inspected file contains no suspend/hibernate/poweroff action. Read-only `/etc/UPower/UPower.conf` reports `CriticalPowerAction=Auto` and `AllowRiskyCriticalPowerAction=false`; that does not establish its effective emergency execution path. Do not claim the companion preserves every emergency policy without inspecting/testing that actual path. The backend acquires no shutdown inhibitor. [DMS battery source](https://github.com/AvengeMedia/DankMaterialShell/blob/v1.6.3/quickshell/Services/BatteryService.qml#L220-L270), [login1 authorization/override API](https://github.com/systemd/systemd/blob/v257/man/org.freedesktop.login1.xml#L798-L840).

## Activity evidence and policy

Use all local environment shell rows, not only the selected UI thread. Prefer `activityRunStatus` over latest-run `status`: projection derives activity from eligible runs, and excludes silent idle-compaction activity. `waiting` is explicitly treated as settled work awaiting checkpoints, not proof a process is executing. [ProjectionStore activity derivation](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/apps/server/src/orchestration-v2/ProjectionStore.ts#L1550-L1662), [activity eligibility](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/apps/server/src/orchestration-v2/ProjectionStore.ts#L1710-L1752), [background derivation](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/packages/shared/src/orchestrationV2PendingBackgroundWork.ts#L29-L105).

The following is the recommended policy, with explicit limits rather than stronger inferred guarantees:

| Observable condition | Policy and qualification |
| --- | --- |
| Preparing/starting/running own turn | Hold, unless blocked by user input or solely a thread/delegate wait. Includes waiting for a synchronous tool/process completion while the run stays active. |
| Plain waiting/checkpoint/queued/completed | No hold from status alone; inspect independent background evidence. |
| Blocking approval/user input | Stop counting that own turn; concurrent local children/background work can still count. `blocking:false` does not stop the turn. |
| Parent blocked solely on thread/delegate wait | Count executing local child rows independently; remote-only waiting does not justify holding this host. |
| Settled run + awaited command/monitor | Hold under the reporting contract, including after the parent finishes. Exclude `pull-request-watch:` synthetic monitors by policy. |
| Unawaited command/devserver | Do not hold from that background summary. |
| Native subagent summary without child row | Evidence of background work, but incomplete locality and input-blocking evidence; cannot strictly guarantee LOCAL-only. |
| App child ID | Follow that child's qualifying state in this environment; missing local child is not proof of local execution. |

Owning sources: [pending task schema, awaited is optional literal true](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/packages/contracts/src/orchestrationV2.ts#L1005-L1038), [thread shell fields](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/packages/contracts/src/orchestrationV2.ts#L2080-L2135), [thread-wait derivation](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/packages/shared/src/orchestrationV2PendingBackgroundWork.ts#L54-L105), [pending extraction and PR monitor construction](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/packages/shared/src/orchestrationV2PendingBackgroundWork.ts#L178-L314).

### Is `awaited` necessary or sufficient?

Neither universally. For commands/monitors **after settlement**, upstream's completion predicate requires `awaited`; an unmarked finite test command can therefore be missed by the companion. Foreground execution does not require this marker. Upstream counts subagents and `background_task` by kind without it, whereas this companion counts non-subagent tasks only when awaited. That is a narrower deliberate policy with possible false negatives, not complete upstream completion parity. Provider support also varies: the management service explicitly handles “provider cannot mark background work awaited.” [Upstream completion predicate](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/packages/shared/src/orchestrationV2PendingBackgroundWork.ts#L89-L110), [management implementation](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/apps/server/src/orchestration-v2/ThreadManagementService.ts#L320-L345).

`awaited:true` is agent/reporting intent, not a finite-process classification or host proof. A mistakenly awaited devserver still holds; PR watch records are explicitly constructed as awaited monitors. No title/command-name heuristic repairs that reliably. [PR-watch construction](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/packages/shared/src/orchestrationV2PendingBackgroundWork.ts#L287-L314).

**Raw shell running can still mean “only waiting for a devserver.”** The background derivation immediately returns an empty list while any active run exists. Its special blocked-wait detector recognizes `t3_thread_wait` and `delegate_task(mode=wait)`, not arbitrary command waits. Inference: a foreground long-running server or process poll is indistinguishable from a finite build/test wait from these shell fields alone. Counting every active foreground run necessarily permits this false hold; excluding every wait would miss the user's required process-completion waits. [Active-run gate](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/packages/shared/src/orchestrationV2PendingBackgroundWork.ts#L235-L259), [blocked-wait algorithm](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/packages/shared/src/orchestrationV2PendingBackgroundWork.ts#L54-L86).

Locality has a similar information boundary. Full projections have `remoteChild` handling, but the pending shell task summary has no universal execution-environment field. Native anonymous summaries cannot prove host locality; app child IDs should be joined only against local rows. A loopback URL is a configured trust boundary, not proof against SSH forwarding. Strict LOCAL-only would require skipping ambiguous summaries (missing some real native work), or upstream adding locality to the public shell summary. [Remote projection selection](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/apps/server/src/orchestration-v2/ProjectionStore.ts#L6640-L6665), [summary construction](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/packages/shared/src/orchestrationV2PendingBackgroundWork.ts#L178-L201).

## Stream synchronization and disconnects

Subscribe via authenticated `orchestration.subscribeShell`, protocol 2, with `requestCompletionMarker:true`. Use a fresh authoritative snapshot on each connection, stage updates/removals, and commit only at `synchronized`. Marked `resolvedRepositoryIdentityRoots` snapshots are project enrichment and must not erase threads. Sequence gaps/coalescing are legitimate; don't require contiguous numbers or discard every equal-sequence entity update. [ShellStream initial/enrichment handling](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/apps/server/src/orchestration-v2/ShellStream.ts#L468-L625), [server subscription and completion marker](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/apps/server/src/ws.ts#L1080-L1280).

A bounded monotonic reconnect grace is an application policy, not an upstream promise: preserve the last hold for e.g. 30 seconds from the first disconnect, never extend it for incomplete reconnects, and clear the deadline only after synchronization. After grace release, work may still exist; indefinite retention would instead risk permanent stale inhibition. Auth/schema failure should release and require repair. Existing `ShellState` and `HoldController` implement this general strategy. [Local state logic](../lib/activity.mjs), [grace controller](../lib/inhibitor.mjs), [existing protocol notes](protocol.md).

## Authentication choice

Prefer the already-supported UI authorized-client pairing flow with only `orchestration:read`; exchange the bootstrap through `/oauth/token`, verify effective session permissions and identity, obtain an RPC WebSocket ticket, and subscribe. Without a proof-key thumbprint, current source issues Bearer sessions and intersects requested scopes with the grant. This creates an authorized client session, **not an additional Connect host**: the exchange path calls the session store, not host registration. Read-only orchestration is broader than status-only; it should not be described as a narrowly isolated activity permission. [Exchange implementation](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/apps/server/src/auth/EnvironmentAuth.ts#L956-L1015), [RPC authorization](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/apps/server/src/auth/RpcAuthorization.ts), [auth HTTP contracts](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/packages/contracts/src/environmentHttp.ts).

Official `t3 auth session issue` exists for scoped headless Bearer issuance. Do **not** invoke it during this research: it loads `EnvironmentAuth.layerRuntime`, which loads the configured SQLite persistence and server-secret storage; it is not a read-only HTTP client. It can open/write storage and carries initialization/migration risk against live state. No credential issuance was performed. [CLI command and runtime loading](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/apps/server/src/cli/auth.ts#L28-L48), [issue command](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/apps/server/src/cli/auth.ts#L166-L200), [storage layer](https://github.com/pingdotgg/t3code/blob/310a0d51942ad742678e9f50783e34967de11b12/apps/server/src/auth/EnvironmentAuth.ts#L1464-L1470).

## Implementation assessment and next decision

The existing backend and snapshot/grace approach are appropriate. The material gaps in `lib/activity.mjs` are semantic: foreground devserver waits can hold; unawaited finite work can be missed; generic background tasks are treated more narrowly than upstream; anonymous subagents can hold for remote or input-blocked work. These follow directly from the derivation and schema limits above. Counting awaited monitors also extends beyond literal local process execution (some monitors just observe external work). Treat these as declared policy/coverage limits until upstream provides enough metadata; do not add process scanning, database reads, or command-name guesses as purported fixes.

Installer work can proceed independently. Before activation, choose whether ambiguous anonymous subagents favor preserving local work or enforcing strict locality; current implementation favors preserving work. No activity-only shell policy can simultaneously eliminate all these false positives and false negatives. A future precise contract needs execution locality, finite/persistent classification, independent runnable/background state during foreground runs, and provider coverage. This is an inference from the cited information gaps, not an existing T3 guarantee. Live authenticated observe-mode compatibility and actual desktop inhibitor behavior remain unverified and require a separately authorized activation check.
